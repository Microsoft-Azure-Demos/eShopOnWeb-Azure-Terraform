# eShopOnWeb – Azure Infrastructure with Terraform

## 1. Overview

This project provisions and manages the Azure infrastructure required to host the **eShopOnWeb** application using Terraform.

The objective is to build a modular, reusable, and maintainable Infrastructure as Code (IaC) solution while applying practical Azure cloud infrastructure, automation, and security practices.

The infrastructure includes:

- Azure App Services hosting the Web MVC application and Public API.
- Azure SQL Server with two databases.
- Azure Storage Account for catalog images.
- Azure Key Vault for application secrets.
- Microsoft Entra ID and Managed Identities.
- Azure Role-Based Access Control (RBAC).
- Reusable Terraform modules.
- Separate Terraform states for infrastructure, Key Vault, and database permissions.

## 2. Architecture

Both applications share a Linux App Service Plan.

The Web MVC application and Public API communicate with Azure SQL and use Managed Identities to authenticate with Azure services.

### High-level architecture

```text
                     Microsoft Entra ID
                            |
                     Managed Identities
                            |
              +-------------+-------------+
              |                           |
         Web MVC App                 Public API
              |                           |
              +-------------+-------------+
                            |
                   Azure App Service Plan
                            |
             +--------------+--------------+
             |              |              |
         Azure SQL     Azure Storage   Azure Key Vault
             |          Account              |
        +----+----+     Catalog Images   JWT Signing Key
        |         |
    CatalogDb  IdentityDb
```

**Storage architecture:** CatalogDb and Azure Storage serve complementary purposes. The database stores catalog information, while the Storage Account holds the actual image files. The applications use image references to retrieve the corresponding blobs.

### Terraform architecture

- `bootstrap/` provisions the Azure resources required for Terraform remote state.
- `environments/infrastructure/` manages the main Azure application infrastructure.
- `environments/key-vault/` manages persistent Key Vault resources independently.
- `environments/database-permissions/` manages SQL database users and permissions for application Managed Identities.
- `modules/` contains reusable Terraform modules shared across configurations.
- `documentation/` contains deployment guides, application settings references, troubleshooting notes, and screenshots.

This structure separates reusable infrastructure logic, application infrastructure, persistent security resources, and database authorization.

### Terraform modules

| Module | Responsibility |
|---|---|
| `resource-group` | Creates the Azure Resource Group |
| `storage` | Creates the Storage Account, blob container, and image blobs |
| `app-service` | Creates and configures Linux App Services; instantiated for both applications |
| `sql-database` | Creates Azure SQL databases; instantiated for CatalogDb and IdentityDb |

### Separate Terraform configurations

Each configuration has its own Terraform state:

| Configuration | Responsibility |
|---|---|
| `bootstrap/` | Creates the remote state backend resources |
| `environments/infrastructure/` | Manages the main Azure infrastructure |
| `environments/key-vault/` | Manages Azure Key Vault independently |
| `environments/database-permissions/` | Manages SQL database users and permissions |

The main infrastructure configuration consumes the separately managed Key Vault state through `terraform_remote_state`.

## 4. Security and Authentication

### Managed Identity

Both App Services use system-assigned Managed Identities.

A Managed Identity provides an automatically managed identity in Microsoft Entra ID. Azure services can use this identity to authenticate without requiring usernames, passwords, or long-lived credentials in application configuration.

### Azure Key Vault and JWT Signing Key

The JWT signing key is stored in Azure Key Vault.

**What is the JWT signing key used for?**

JSON Web Tokens (JWTs) are commonly used to authenticate users and authorize access to protected application endpoints.

When a token is issued, the application signs it using the signing key. The receiving application can verify the signature to confirm that the token was issued by a trusted party and has not been tampered with.

The signing key must therefore be kept secret.

Both App Services receive the **Key Vault Secrets User** role through Azure RBAC.

### How App Service Key Vault References Work

Instead of placing the actual JWT signing key directly in App Service configuration, the application settings use a Key Vault reference.

For example:

```text
@Microsoft.KeyVault(SecretUri=https://<vault-name>.vault.azure.net/secrets/jwt-signing-key)
```

App Service resolves the reference using its Managed Identity and retrieves the secret from Key Vault.

This avoids hardcoding the actual signing key in Terraform configuration or application settings.

### Independent Key Vault Lifecycle

Key Vault is managed independently through `environments/key-vault/`.

This separation is intentional: the Key Vault and its JWT signing key can persist while the application infrastructure is redeployed during development and testing. The secret does not need to be recreated or entered again for every application infrastructure deployment.

For production environments, Key Vault provisioning could also be integrated into a broader infrastructure deployment, depending on the required resource lifecycle and security architecture.

### Azure SQL Authentication

The SQL Server is configured for Microsoft Entra-only authentication.

Both applications authenticate using their Managed Identities.

The SQL connection strings use:

```text
Authentication=Active Directory Managed Identity;
```

This eliminates the need to store SQL usernames and passwords in application configuration.

### Terraform State

Terraform state is stored remotely in Azure Blob Storage.

Separate state files are used for the independently managed configurations. The main infrastructure configuration also reads the Key Vault state using `terraform_remote_state`.

Terraform state may contain sensitive infrastructure information. Access to the state storage account and container must therefore be restricted.

## 5. Container Deployment

Both applications run as Linux containers on Azure App Service.

### Web MVC

- Image: `egamor/eshopwebmvc-azure:1.0.0`
- Target port: `8080`
- Container authentication type: `Anonymous`
- Hosting platform: Linux App Service

### Public API

- Image: `egamor/eshoppublicapi-azure:1.0.0`
- Target port: `8080`
- Container authentication type: `Anonymous`
- Hosting platform: Linux App Service

Application-specific environment variables and connection settings are configured through App Service application settings.

### Parameterized Configuration

The Terraform modules use variables to make the infrastructure reusable.

For example:

- Container image names can be changed without modifying module implementation.
- Database names are configurable.
- Storage account and container names are configurable.
- Application names and hosting regions are configurable.
- Image files can be replaced with other catalog images.
- Application settings are maintained separately from reusable Terraform module logic.

The JSON application settings files are located in [`documentation/app-settings/`](./documentation/app-settings/). This approach separates reusable infrastructure logic from application-specific configuration, making the Terraform modules easier to reuse and maintain.

## 6. Deployment Guide

Install and configure:

- [Terraform](https://developer.hashicorp.com/terraform/install)
- [Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli)
- An active Azure subscription.
- Appropriate Azure permissions to provision resources and configure RBAC.
- Access to the Terraform remote state storage.

Authenticate with Azure:

```powershell
az login
```

### Step 1 – Bootstrap Terraform Remote State Infrastructure

Create the Azure resources required for the Terraform remote backend.

This includes the Resource Group, Storage Account, blob container, and required RBAC assignment.

Follow the instructions in:

### Step 2 – Configure Terraform Remote State

Each configuration uses its own state key to keep its state independent.

Follow the instructions in:

[2. Configuring Terraform remote state](./documentation/2.terraform-remote-state-setup.md)

### Step 3 – Provision Azure Key Vault

Deploy the persistent Key Vault infrastructure and configure the JWT signing key.

Follow the instructions in:

[3. Deploying Azure Key Vault](./documentation/3.key-vault-setup.md)

### Step 4 – Provision the Main Infrastructure

Before deploying the infrastructure, review and update `terraform.tfvars` to match your environment and deployment requirements.

One required variable is `sql_entra_admin_object_id`, which specifies the Object ID of the Microsoft Entra ID user who will be configured as the Azure SQL Server administrator.

To retrieve the Object ID of the currently authenticated user, run the following command in PowerShell:

```powershell
# Retrieve the Object ID of the currently authenticated Microsoft Entra ID user.
az ad signed-in-user show --query id --output tsv
```

Copy the returned Object ID and assign it to `sql_entra_admin_object_id` in `terraform.tfvars`.

Once the configuration is updated, follow the deployment instructions in:

[4. Deploying the main infrastructure](./documentation/4.deploy-infrastructure.md)

### Step 5 – Configure Database Permissions

Configure SQL database users and permissions for the Web MVC and Public API Managed Identities.

Follow the instructions in:

[5. Configuring SQL database permissions](./documentation/5.sql-database-permissions.md)

### Step 6 – Verify the Deployment

Verify that the Azure resources have been deployed and that the application endpoints are reachable.

Follow the instructions in:

## 7. Issues Encountered and Resolutions

### Azure SQL Managed Identity – SID Mismatch

**Problem:** The Terraform provider `muecahit94/mssql` successfully created database users and assigned roles, but both applications failed to authenticate.

The application logs showed:

```text
Login failed for user '<token-identified principal>'.
```

The issue was traced to a mismatch between the SID associated with the database users created through the provider and the authoritative Microsoft Entra identity SID.

**Resolution:** The affected database users were removed and recreated using native Azure SQL commands:

```sql
CREATE USER [eshop-dev-webmvc] FROM EXTERNAL PROVIDER;
CREATE USER [eshop-dev-publicapi] FROM EXTERNAL PROVIDER;
```

The required database roles were then assigned to the recreated users.

This was performed in both `CatalogDb` and `IdentityDb`.

Detailed troubleshooting and recovery steps are documented in:

[7. Troubleshooting database authentication errors](./documentation/7.login-failed-error-resolutions.md)

**Automation consideration:** To avoid the SID mismatch encountered with the provider, database user creation can be automated using a `terraform_data` resource with a `local-exec` provisioner that executes native SQL commands using an authenticated Azure CLI access token. Such automation should be implemented with appropriate execution, permission, and state-management considerations.

## 9. Security Considerations

- Never commit Terraform state files or state backups.
- Never commit passwords, credentials, JWT signing keys, or other secrets.
- Keep sensitive `terraform.tfvars` files out of Git.
- Use Managed Identities instead of long-lived credentials.
- Use Azure RBAC to control access to resources.
- Restrict access to remote Terraform state.
- Avoid broad SQL firewall rules in production.
- Remove temporary testing firewall rules before production deployment.
- Review Terraform plans before applying infrastructure changes.
- Keep generated Terraform working directories out of source control.

**Development warning:** The current development configuration includes a temporary SQL firewall rule named `AllowAllForTesting`, which permits connections from all public IPv4 addresses. This is intended for testing only and must not remain enabled in production.
